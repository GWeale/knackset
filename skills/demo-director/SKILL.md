# Direct a demo that proves something

Make the viewer understand one worthwhile change. Deliver the requested script,
storyboard, or film; when a film is requested, carry production as far as available
tools and authorization permit. A production plan alone is not a rendered video.

## Discover what can be shown

Inspect the supplied product, artifact, source, recordings, or screenshots. Use
current working behavior as the strongest evidence. Distinguish running features,
static mockups, proposed behavior, and assertions in old sales material. Note the
version or supplied evidence when it affects what can honestly be demonstrated.

Identify the audience, desired understanding or action, channel, duration, aspect
ratio, and available assets. Reuse settled context. Ask only for a consequential
missing choice; otherwise state a reasonable assumption and proceed. Honor an
explicit script or visual direction while correcting unsupported factual claims.

Use synthetic or approved demonstration data. Opening a product for recording
does not authorize live transactions, messages, account changes, or publication.
Keep the demo inside the authorized environment and avoid incidental private data.
Do not purchase services, clone a voice, or install a production stack to fill an
unannounced capability gap.

## Choose the proof

Name what the viewer should believe after watching, then find the visible state
change or artifact detail that earns that belief. Prefer a small complete action
with a readable result over a tour of controls. If a claimed capability cannot be
shown or supported, name the gap and build around the closest real capability.

Structure the sequence around the viewer's question: establish the relevant
starting state, show the meaningful action, hold on the result, and explain its
consequence only where the picture needs help. Use a recurring visual cue when
it helps people follow a concept across scenes. A longer workflow may need several
proof beats; a short one should not acquire a feature list to fill time.

Keep an honest relationship between time and action. Label a time skip, mockup,
or simulated result when it would otherwise imply real behavior. Do not present
an edited wait as measured performance, a scripted run as autonomous capability,
or a fabricated screen as a capture of the working product.

## Write the cut before producing it

Make a timed script and storyboard. For each beat specify what is visible, the
action or transition, narration or on-screen words, and the evidence it supplies.
Give important results enough time to read. Budget the actual spoken text and
transitions rather than assigning arbitrary timestamps to an overlong script.
A silent demo should still explain the change; captions should not merely repeat
unreadable interface text.

When using a reference film, inspect frames and timing if available. Extract its
editing rules: where cuts land, how framing directs attention, what captions do,
and where sound or silence changes the energy. Apply those rules to this story's
beats. Do not copy the reference's footage, script, or exact cut schedule.

## Produce and verify

Use the simplest available route that fits the deliverable: screen capture,
editable motion code, an animatic, or a supported video tool. Preserve usable
source and keep effects subordinate to the proof. Use real interface material
when accuracy matters. Separate illustrative inserts from product evidence.

Inspect the resulting media when possible: key frames for legibility and layout,
then playback for pacing, transitions, and audio synchronization. Confirm that
each promised result appears and that narration matches the state on screen.
A contact sheet cannot establish motion or sound quality. If capture or rendering
is unavailable, finish the script, storyboard, captions, and usable production
source; state the exact missing step and label the result prepared.

Deliver actual file links and formats, a brief account of what the demo proves,
and any material production limits. Distinguish a filmed interaction, a simulated
animatic, and an unrendered source. Keep the package ready for the user's next
step without assuming permission to upload, send, publish, or change a service.
